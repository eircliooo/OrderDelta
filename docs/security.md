# 安全说明

> 对应 [`SPEC.md`](SPEC.md) §15。本文给出威胁模型、SPEC §15 每一条的**实际落实状态**，
> 以及当前明确存在的安全限制。
>
> 状态标记：✅ 已实现 · ⚠️ 部分实现 · ⬜ 未实现。
> **写「已实现」必须能指到具体文件行。** 未实现的条目一律如实标注，不写「基本完成」。

---

## 0. 一句话结论

**本工具是单机、单用户、无身份认证的本地程序。它唯一的访问控制手段是「只监听
`127.0.0.1`」。把监听地址改成 `0.0.0.0`，等于把全部客户订单数据无密码公开给整个局域网。**

---

## 1. 威胁模型

### 1.1 保护对象

| 资产 | 敏感性 | 位置 |
|---|---|---|
| 客户订单原始文件（`.xlsx`） | **高**——含客户名、单价、成本结构、付款条件 | `data/files/`，随机 UUID 文件名 |
| 提取出的字段与差异结果 | **高**——同上 | `data/orderdelta.sqlite3` |
| 人工审核备注 | 中——含商务判断 | `data/orderdelta.sqlite3`，**并且会出现在导出的 HTML 报告里**（见 §4.5） |
| 导出的 HTML 报告 | **高**——会被主动发给老板 / 客户 | 用户自行保存的位置 |

**这类数据泄露的后果是具体的**：单价和成本结构落到同行手里会直接影响报价谈判。
所以本文档不把「反正是内网工具」当成任何一条的理由。

### 1.2 明确纳入威胁模型的攻击者

| 攻击者 | 能力 | 主要攻击面 |
|---|---|---|
| **恶意上传文件** | 用户被诱导上传一份精心构造的 `.xlsx`（例如客户邮件里的附件） | 解析器：解压炸弹、超大工作表、伪装扩展名、加密文件、宏 |
| **文件内容注入** | 攻击者控制单据里的文本（买方名、备注、品名） | HTML 报告 XSS、Excel 公式注入、日志注入 |
| **同一局域网的其他人** | 能访问本机的网络端口 | HTTP 接口（**无认证**） |
| **拿到导出报告的人** | 只有报告文件 | 报告里是否含额外信息、是否会回连外网 |

### 1.3 明确排除在威胁模型之外的（MVP 的诚实边界）

| 不防的 | 为什么 |
|---|---|
| 能在本机以同一用户身份执行代码的人 | 他可以直接读 `data/` 目录。任何应用层措施都是摆设。 |
| 物理接触磁盘的人 | 应对手段是整盘加密（BitLocker），不是应用程序。 |
| 本机上的其他本地进程 | 回环端口对本机所有进程可见。MVP 单用户桌面场景下接受这个风险。 |
| 供应链攻击（依赖包被投毒） | 已记入 [`future-scope.md`](future-scope.md)，MVP 不做依赖锁定与校验。 |
| 恶意的**本工具使用者** | 他就是数据所有者。 |

### 1.4 三条基础安全假设

1. **本机是可信的。** 用户在自己的工作电脑上运行，操作系统账户即身份边界。
2. **服务只监听回环地址。** 这是替代身份认证的手段（SPEC §15.2 第 3 条）。
3. **不联网。** MVP-0 不调用任何外部服务，没有遥测、没有模型 API、没有崩溃上报。

**这三条里任何一条被打破，本文档的安全结论都不再成立。** 尤其是第 2 条。

### 2.3 「安全删除」措辞（SPEC §15.3）

在 SQLite + 普通文件系统 + SSD 上**无法真正安全擦除**（写时复制、磨损均衡、日志文件、
WAL、系统还原点都会留下副本）。

**因此本项目一律表述为：**

> 删除项目会**删除数据库记录与磁盘上的原始文件**。

**禁止**出现「安全擦除」「彻底清除」「不可恢复」之类措辞。这条约束同时写在
`CLAUDE.md`、`README.md`、`services/projects.py::delete_project` 的文档字符串里。

对确实敏感的数据，正确的手段是**整盘加密**（BitLocker / FileVault），不是应用层删除。

## 3. SPEC §15.2 新增四条

### 3.1 Excel 公式注入 ⬜ 未实现（当前不适用）

**规格**：导出 Excel 时所有**文档来源字符串**必须走同一个 helper，`cell.value = s` 之后
强制 `cell.data_type = "s"`。**不加 quotePrefix，不枚举 `+ - @ TAB`。**

**当前状态**：MVP-0 **没有 Excel 导出**（属 MVP-1），因此这条暂不适用。
但落地时必须实现，理由比常规安全场景更硬：

> 客户报价单里把 `line_total` 写成 `=D5*E5` **极其常见**。作为证据文本原样写进导出报告后，
> Excel 会按**报告自己的网格**重新求值，在一个声称「引用原文」的位置静默显示一个错数字。
> 这不是攻击，是日常，而且它比 XSS 更难被发现。

openpyxl 对 `=` 开头的字符串**默认置为公式类型**，不处理即中招。

### 3.2 HTML 报告 ✅ 已实现

`app/exports/html.py`，三条逐条落实且都有测试：

| 措施 | 实现 | 测试 |
|---|---|---|
| Jinja2 **显式 `autoescape=True`**（默认是 `False`） | `Environment(autoescape=True, undefined=StrictUndefined, ...)` | `test_单据里的script标签被转义为实体`、`test_项目名里的html被转义`、`test_生成时间里的html被转义` |
| `<head>` 内嵌 CSP meta | `default-src 'none'; style-src 'unsafe-inline'; img-src data:` | `test_head内含csp_meta` |
| **报告零 JS**（折叠只用 `<details>`） | 模板中无 `<script>`、无事件属性 | `test_报告零js`、`test_折叠使用details元素` |
| 无任何外部引用 | 样式全部内联 | `test_文件内无任何外部http引用`、`test_不引用任何外部资源标签` |

`autoescape=True` **是这份模板唯一的 XSS 防线**。单据里的备注、买方名称、品名全是
用户可控文本，会原样进报告。Jinja2 的默认值是 `False`——不写就是漏洞。

`StrictUndefined` 是另一层保险：模板里的字段笔误在测试期就炸掉，而不是静默渲染成空白。

报告可以断网、后端停机打开（Gate-0 第 12 条），这既是可用性要求，也是安全属性：
**一份不会回连任何地址的报告，转发出去不会附带泄露任何行为信息。**

### 3.3 绑定地址 ✅ 已实现

```python
# app/core/config.py
class Settings(BaseSettings):
    #: 监听地址。**默认回环**，这是本 MVP 唯一的访问控制手段。
    host: str = "127.0.0.1"
    port: int = 8000
```

`.env.example` 里逐字写明了后果：

> **改成 0.0.0.0 会让同一局域网内任何人无需密码打开你的订单数据。**

**禁止由此引入登录 / Token / HTTPS / 限流。** 回环绑定就是本 MVP 替代鉴权的廉价手段。
半吊子的自研认证比没有认证更危险——它会让人以为可以安全地暴露出去。

如果确实需要局域网访问，正确做法是**在前面加一层带认证的反向代理**，而不是把
`ORDERDELTA_HOST` 改成 `0.0.0.0`。

### 3.4 CORS ✅ 已实现（靠不需要它）

前端 API base 一律走**相对路径 `/api`**，开发期由 Vite dev proxy 转发到
`http://127.0.0.1:8000`（`frontend/vite.config.ts`），生产期由 FastAPI 自己静态托管
`frontend/dist`（`app/main.py`）。

因此**全程同源，不需要 CORS 中间件，代码里也确实没有**。

这是唯一有返工代价的一条：一旦在前端硬编码了 `http://localhost:8000`，
后面改同源代理要动每一个调用点。

若将来确需 CORS，只允许**显式列表**，**禁止 `"*"`**。

## 4. 当前明确存在的安全限制

**这一节请完整读完再决定是否把它接触真实订单数据。**

### 4.1 没有任何身份认证 —— 靠回环绑定保护

- **没有登录、没有用户、没有权限、没有会话、没有审计日志。**
- 能访问 `http://127.0.0.1:8000` 的**任何本机进程**都能读写全部数据。
- 唯一的边界是操作系统账户 + 只监听回环。

⚠️ **不得把监听地址改成 `0.0.0.0`。** 这不是配置偏好，是本 MVP 的安全模型基础。
一旦改掉，同一局域网内任何人无需密码即可读取、导出、删除你的全部订单数据。

⚠️ **同样不得把它部署到任何服务器上。** SPEC §1.2 的「坚决不实现」清单里
「生产部署」赫然在列，原因正是这一条。

### 4.2 处理超时未强制执行

`ParseLimits.timeout_seconds = 30` 这个字段**存在但没有任何代码使用它**。

实际后果：一份构造得当的 `.xlsx`（在行数、工作表数、解压体积、压缩比全部合规的前提下
仍然解析极慢）可以让一次上传请求长时间占用一个工作线程。**这是一个已知的拒绝服务风险。**

现有缓解（都是间接的，不能替代超时）：

- 上传 20MB 上限、解压 300MB 上限、压缩比 200:1 上限
- 工作表 ≤ 20、每表 ≤ 5000 行、合计 ≤ 20000 行，且**边遍历边判**
- 单机单用户场景下，攻击者要先把文件送到用户手里并说服他上传

**为什么字段留着却不实现，而不是把字段删掉？** 两个理由都写在
`app/parsers/base.py::ParseLimits.timeout_seconds` 的注释里：

1. **不能在解析器内部实现。** 真正耗时的是 openpyxl 的 `load_workbook` 本身，
   它不可中断；在可中断的行遍历里插一个墙钟判断只挡得住构造得极巧的输入，
   却把系统时钟读进了解析路径——而「同一输入两次解析结果一致」是 Gate-0 第 15 条。
   **一个会让确定性验收失效的超时，比没有超时更糟。**
2. **不能删掉字段。** 本文 §4.2、[`limitations.md`](limitations.md) §6.2、
   `README.md` §14 第 10 条都把「解析超时尚未实现」列为已知风险；
   删了字段，这三处就指向一个不存在的东西。

**正确的落地位置是请求层**（独立进程 / worker 加墙钟），不在解析器内部。
已记入 [`future-scope.md`](future-scope.md) §6。

### 4.3 上传文件的解析在请求线程内同步进行

`POST /api/v1/projects/{id}/documents` 会**在请求处理过程中**完成解析。
配合 §4.2 的「超时未强制执行」，这意味着单次上传的耗时上界只由文件大小、行数、
工作表数等静态上限间接约束。

单机单用户场景下影响有限；但它是 §4.2 那条风险能被触发的原因，两条应当一起看。

> 恶意文件的**拒绝路径**本身已有逐条测试覆盖（见 §2.1 第 18 条与
> [`limitations.md`](limitations.md) §6.3）。本条说的是**通过校验之后**的处理时长。

### 4.4 依赖供应链未加固

- 没有依赖锁文件（后端无 `requirements.lock` / `uv.lock`；`pyproject.toml` 用的是范围约束）
- 没有哈希校验、没有 SBOM、没有漏洞扫描

单机场景下风险有限，但在企业环境里这是必须补的一环。已记入 future-scope。

### 4.5 报告文件的后续流转不受控

导出的 HTML 报告本身是安全的（零 JS、无外部引用、内容已转义），但**它包含完整的
订单数据**。一旦用户把它发出去、传到网盘、放进共享目录，工具无法也不应该介入。

⚠️ **报告还会带上你写的审核备注**（`app/exports/html.py` 的「人工裁决」列，
一条都没裁决过时该列不渲染）。备注是给自己看的商务判断——
「这家客户上次也这么砍价」「等张总回话」之类——**它会随报告一起发给收件人**。
写备注时请按「会被客户读到」来写，或者在导出前先改掉。

**报告不带任何水印、不带访问控制、不会过期。** 请按普通机密文件对待。

### 4.6 无备份、无事务级恢复

`data/` 目录被误删就没了。工具不做自动备份。**这是刻意的**——自动备份会在用户
不知情的位置留下订单数据副本，与「删除项目会删除数据库记录与磁盘上的原始文件」
这条承诺直接冲突。

需要备份请自行复制 `data/` 目录，并意识到副本同样敏感。

## 5. 给 IT / 安全评审的检查清单

如果你要评估能否在公司环境里使用，按这个顺序看：

1. **它监听在哪里？** `app/core/config.py` 的 `host` 必须是 `127.0.0.1`。
   运行时可用 `netstat -ano | findstr :8000` 确认。
2. **它出网吗？** `app/` 下 grep `requests|httpx|urllib|socket` 应为空。
   也可以直接断网跑一遍全流程。
3. **数据落在哪里？** `data/orderdelta.sqlite3` 与 `data/files/`，都在仓库目录下，
   已被 `.gitignore` 排除。
4. **报告会回连吗？** 用文本编辑器打开导出的 HTML，搜索 `http://` 与 `https://`——
   应为零命中（有机械断言 `test_文件内无任何外部http引用`，同时还查 `//cdn`）。
   注意**不要只搜裸的 `http`**：`<head>` 里的 CSP `<meta http-equiv=...>` 会命中它，
   那是本地安全头，不是外链。
5. **谁能访问？** 本机该操作系统账户下的任何进程。**没有更细的粒度。**
6. **它会执行上传文件里的东西吗？** 不会：拒绝 `.xlsm` / `.xlsb`，openpyxl 不执行宏，
   报告零 JS。
7. **未覆盖的风险？** 见 §4，尤其是 §4.2 的超时未强制执行。

**结论建议**：适合个人在自己的工作电脑上作为辅助核对工具使用；
**不适合**部署为共享服务、不适合放在服务器上、不适合处理需要审计追溯的数据。
